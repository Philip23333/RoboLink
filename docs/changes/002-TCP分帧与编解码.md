# 修改说明：TCP 分帧与 Protobuf 编解码

日期：2026-10-19
提交状态：未创建 Git 提交

## 本次完成

上一阶段已经确认 Java、Python、TypeScript 能读懂相同的消息格式。这一步让 Java 网关具备从连续 TCP 数据中找出完整消息的能力，并能按同样格式发送消息。

机器人把消息分几次送达，或者多条消息一起送达时，网关现在能够按顺序还原。遇到长度非法、数据损坏或版本不支持的消息，会关闭连接。

## 技术栈的应用与做法

### 场景一：机器人连续报告位置，数据分几次到达

设想 RB-001 先报告“电量 87%，位置 x=1.25、y=-2.5”，紧接着又报告新的位置。机器人发出了两条消息，但 TCP 向服务器提供的是连续字节，服务器一次读取的数据不一定刚好等于一条消息。

可能出现以下情况：

| 到达情况 | 本次处理方式 |
| --- | --- |
| 先到长度头的前 2 字节 | 保存并等待，暂时不尝试读取位置 |
| 长度头到齐，但消息体只到一部分 | 根据长度知道还缺多少，继续等待 |
| 两条完整消息一起到达 | 分成两条，按原顺序分别处理 |
| 一条完整消息加半条下一条消息 | 先交付第一条，再等待第二条剩余内容 |

**Netty 负责找出每条消息的边界，这个过程叫“分帧”。** 每条消息前加 4 字节长度头，写明后面的消息体有多少字节。项目使用 Netty 已有的长度分帧组件完成等待和拆分，并额外拒绝长度为零的消息。

**Protobuf 负责把完整消息体还原成有意义的字段。** Netty 找齐一条消息后，去掉长度头，再由 Protobuf 读取 robot_id、电量和坐标。这样未到齐的半条消息不会提前进入业务处理。

每个连接有自己独立的接收缓冲，因此 RB-001 正在等待后半条消息时，不会把另一台设备的数据拼进来。连接断开后，尚未接收完整的数据会被释放，不会凭空补成一条状态。

### 场景二：服务器准备向机器人发出消息

本次发送流程与接收相对应：

```text
Java 中的 Envelope 消息
          ↓ Protobuf 编码
二进制消息体
          ↓ Netty 补上 4 字节长度头
可以发给 TCP 连接的数据
```

例如后续要发送“前进 1 秒”的指令，业务模块只需提供结构化消息，这一层负责把它变成符合约定的字节。指令应该发给哪台机器人、是否允许执行、怎样等 ACK，仍由后续会话和指令模块实现。

**Netty 的 pipeline 是按顺序组织收发步骤的处理链。** 接收方向先分帧、再解码、再检查消息；发送方向先检查、再编码、再加长度头。业务模块后续可以接在这条处理链之后，不必重复编写字节拼接逻辑。

### 场景三：对方发来不合理的数据

假设对方只发来一个长度头，宣称接下来的消息超过 64 KiB。网关收到这个头后就拒绝连接，不等待对方真的把超大消息发完。大小限制用于约束单条消息，并不表示系统已经完成高并发或弱网验证。

如果长度正常但内容无法按 Protobuf 解析，或者消息版本不是 1、没有具体消息内容，也会关闭连接。同一批数据中即使还跟着正常消息，也不会在连接关闭后继续交给业务处理。

发送方向同样执行检查：如果 Java 业务代码尝试发出超限、缺内容或不符合约定的消息，会报告发送失败，并且不会输出这条消息的字节。设备身份、坐标范围、运动速度等业务规则仍留给后续模块校验。

### 怎样验证这些情况？

**JUnit 用于自动执行测试并报告失败。** 本次增加两类测试：一类在内存中精确控制每次送入多少字节，稳定复现半包、合并和异常数据；另一类真的建立本机 TCP 连接，验证收发流程在实际套接字上可用。

随机拆分测试使用 20 个固定种子，每次连续送入 100 条状态，检查顺序和内容完全一致。固定种子表示同一轮随机拆分可以再次复现，便于排查问题。这是正确性测试，不是压测成绩。

## 验证结果

23 项自动化测试全部通过，失败、错误、跳过均为 0。其中 21 项检查内存中的分帧与边界行为，2 项通过真实本机 TCP 连接检查收发与拒绝超大消息。

第一步三端互通也已回归：Java、Python、TypeScript 的 18 次消息比较全部一致，Java 构建和 TypeScript 类型检查通过。详细结果见 [第二步验收记录](../acceptance-step-02.md)。

真实 TCP 测试中的服务器仅在测试期间启动，收到合法消息后原样回复，用于检查编解码。设备注册、心跳、完整模拟器、WebSocket 和 Vue 页面尚未实现。

日期：2026-10-20

## 本次完成

现在可以同时运行三台软件机器人，持续向网关报告各自的电量、位置和状态。控制客户端发出前进、转向和停止指令后，机器人会计算自己的运动，再通过真实 TCP 连接回传 ACK、执行结果和新位置。网页还没有实现，本次用自动化 WebSocket 客户端验证这条链路。

## 场景一：让 RB-001 前进，另外两台保持原地

控制客户端请求 RB-001 以 0.2 m/s 前进 400 ms。Java Netty 网关把指令转给 RB-001；Python 模拟器检查参数，先回“接受执行”的 ACK，再根据实际经过时间更新位置。到期后停止，返回“执行完成”的 Result，并上报 x=0.08 m；RB-002 和 RB-003 的坐标不变。

**Python asyncio 负责让多台设备同时收发。** 可以理解为设备在等网络消息时，程序先去处理其他设备，而不是每台设备独占一个线程。每台机器人都有自己的 TCP 连接和状态；接收命令、发送消息、运动更新分别协作运行，不用等待某次运动结束才发送心跳。

**Protobuf 负责让两端读懂同一条消息，TCP 长度头负责识别消息边界。** 模拟器沿用现有共享协议，没有另造一套 JSON。读取时先收齐长度头，再按长度读消息体；发送时由一个任务统一安排 ACK、结果、心跳与遥测，避免多个任务把帧和序号发乱。

**本地计时负责决定机器人实际走多远。** 更新周期偶尔迟到时，只计算动作截止时刻之前的运动。例如 400 ms 动作到 450 ms 才被调度，也只走 0.08 m，不多走 50 ms。这使用单调时钟：只衡量过去了多久，不受系统日期调整影响。

## 场景二：重复收到“前进”，不能再走一遍

同一条指令执行完成后再来一次，设备返回已有 ACK 和结果，不重新移动。如果同一个指令编号被改成另一种速度，则拒绝。设备保存有限数量的短期记录：最多 256 条，结束后保留 60 秒；记录到期或进程重启后不承诺去重。

**指令编号承担关联与去重职责，不能代替传输序号。** 同一条指令重发时，网络消息序号可以更新，但 command_id 不变。网关和设备各自做检查，避免只靠网页防止重复点击。

## 场景三：点停止，或云端突然不再回应

RB-003 正在前进时，STOP 会让它结束当前运动。原指令回报“被中断”，STOP 自己回报“成功”，两条结果不会混为一谈。若设备发现 TCP 断开、心跳一直没有对应回复，或发送失败，也会停止本地运动。

**心跳验证的是通信是否仍能往返。** 只要设备还能向外发遥测，并不能证明网关的回复仍能到达。模拟器因此单独等待心跳确认；遥测持续发送也不能把这项检查绕过去。

本次还没有自动重连。命令行运行时一台设备失败会结束整个模拟组；下一步再把各设备的恢复过程独立起来。网络故障从发生到被检测存在时间间隔，本地停止发生在检测到故障时，不宣称瞬间感知断网。

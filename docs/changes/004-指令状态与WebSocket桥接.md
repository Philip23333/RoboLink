## 本次完成

前一步网关已经认识接入的机器人，这一步加入控制客户端，让它可以发出“让 RB-001 前进 1 秒”的请求。网关会找到 RB-001 当前的 TCP 连接，把请求发过去，再把设备确认与执行结果返回给发起请求的客户端。

本轮完成通信与状态处理，控制客户端和设备均可由自动化测试程序扮演。Vue 页面和真正模拟位置变化的 Python 机器人还在后续步骤。

## 技术栈的应用与做法

### 场景一：用户想让 RB-001 前进 1 秒

这条请求需要写清设备编号、唯一指令编号、速度 0.2 米/秒和持续时间 1 秒。

```text
控制客户端发出 Protobuf 二进制消息
            ↓ WebSocket
网关核对权限、参数和设备状态
            ↓ 转成 TCP 长度帧
RB-001 接收指令
            ↓ ACK 与执行结果经 TCP 回来
网关只向原控制会话返回指令状态
```

**Netty 负责连接两种通信通道。** 控制端使用 WebSocket，机器人使用 TCP。两边传的是同一套 Protobuf 消息，但消息边界不同：WebSocket 自身有完整消息边界，TCP 需要补 4 字节长度头。本次把两种接收与发送流程接起来，还处理了 WebSocket 一条消息被拆成多个片段的情况。

**Protobuf 负责表达请求、确认和结果。** 客户端不需要自己拼底层字节；网关也不用把设备数据反复转换成 JSON。新增了专门的控制端认证消息，三种语言仍从同一份协议生成代码。

### 场景二：网关发出去了，是否就算机器人执行成功？

现在把几个不同阶段分开报告：

| 状态 | 在这个场景中说明什么 |
| --- | --- |
| CREATED | 网关接纳请求，开始跟踪 |
| SENT | 本地发送操作成功，尚不能证明设备已接受 |
| ACKED | 设备明确表示接受指令 |
| SUCCEEDED / FAILED | 设备回传完成或失败结果 |
| REJECTED | 网关或设备拒绝请求 |
| ACK_TIMEOUT / RESULT_TIMEOUT | 分别没有及时收到确认或执行结果，实际结果不确定 |
| UNKNOWN | 连接断开、会话替换等原因使结果无法确认 |

**Java 指令状态机负责记住一条请求走到了哪一步。** 它按指令编号关联消息，并核对结果来自原来那台设备的原会话。例如 RB-002 回传了 RB-001 的指令编号，也不能把这条任务改成成功。

ACK 和结果使用两个独立期限，定时等待不会阻塞网络线程。请求超时后，即使迟到一个成功结果，也不会把已结束的状态重新打开。对于已发出但结果不明的运动，网关会暂时阻止新的运动请求，仍允许发送 STOP；超时本身不代表机器人已经停下。

### 场景三：两个客户端同时查看同一台机器人

例如操作员甲和乙都在看 RB-001 的电量，但只有甲发出了前进指令。两人可以按订阅收到遥测，甲的指令确认与执行结果只回到甲原来的 WebSocket 会话。

**独立控制凭证和设备权限负责限制“谁能看、谁能控制”。** 每个控制身份明确配置可访问设备。连接时先检查网页来源和路径，再通过第一条二进制消息提交凭证，密钥不放进 URL。认证前不能订阅或发指令。

如果客户端重复发送同一指令编号和相同参数，网关在短期记录还存在时返回已有状态，不再次发给机器人。换一组参数、换一个控制会话再复用这个编号，会被拒绝。记录默认保留 60 秒，过期和服务重启后的执行去重还需要设备端配合，不能据此宣称“任何情况下只执行一次”。

### 场景四：网页接收速度跟不上机器人上报

如果机器人连续上报电量 87%、86%、85%，但客户端暂时收不动，没有必要为同一设备保留越来越多条旧遥测；本次会合并成最新值。

**有界输出队列负责防止慢客户端无限积压。** 遥测按设备保留最新一条，指令结果和上下线通知进入独立队列。可靠消息队列满了，或者输出持续阻塞，会断开连接，让客户端重新同步，而不是悄悄丢掉某条执行结果。

**一个专用协调线程负责统一处理指令状态。** 设备回包、控制请求和超时可能从不同网络线程到达，统一协调可以避免它们同时修改同一条指令。协调队列也有限额，网络事件循环不做数据库访问或阻塞等待。

## 验证结果

新增 29 项测试全部通过，其中 20 项检查指令状态、去重、权限和慢消费者边界，9 项通过真实 WebSocket / TCP 连接验证握手、分片和双向桥接。加上原有 54 项测试，共 83 项 Java 测试通过，失败、错误、跳过均为 0。

遥测、指令、控制认证请求与认证结果四类样例在三种语言间共 36 次比较全部一致；Java 构建、TypeScript 类型检查和 Python 设备接入主程序的回归也通过。详细结果见 [第四步验收记录](../acceptance-step-04.md)。

真实 WebSocket / TCP 测试已验证指定设备路由、遥测订阅、ACK 和结果返回，以及另一控制客户端收不到该指令状态。测试设备按预设步骤报告结果，本轮没有验证真实或模拟机器人位移，也没有并发性能成绩。

# 独立机器人进程与通信闭环证据

日期：2026-10-20。状态：实现与验收通过。

## 页面怎样体验

启动 `scripts/start-demo.ps1`，打开 http://127.0.0.1:5173，点击「连接本地演示」。

设备状态下方新增「设备进程与 TCP 连接」：三张卡分别给出实际 PID、进程收发计数、网关观察到的 TCP 对端、会话和心跳，以及两端会话是否匹配。进程信息来自本地监督程序，TCP 信息来自认证后的网关快照，不从前端图标数量推导。

发送一条前进指令，在「指令通信闭环证据」中查看同一编号的 11 个环节。可以用下拉框切换指令。网页、网关、机器人各自在处理点采集自己的事件；缺失显示「尚无观测」。本地发送与对端接收分开，既不把 ACK 当执行结束，也不根据状态自动补齐轨迹。

点击「停止 RB-002 进程」，该 Python 进程实际退出、设备离线；其他两台继续上报。如果正在运动，云端指令显示结果未知，不伪造成功。点击「启动 RB-002 进程」后，PID 与网关会话改变，使用停止时保存的模拟位置，不恢复旧运动。

## 实际实现与边界

- 一键演示从一个 Python 进程内的三个协程改为三个独立子进程。监督程序、Java 和 Vite 进程不计入机器人数量。手动 `start-simulator.ps1` 保留原多协程方式用于通信测试，不能将其表述为三个进程。
- Windows 虚拟环境启动器可能产生额外转发进程。本轮实测启动器 PID 与实际解释器 PID 不同，因此监督程序使用项目虚拟环境对应的基础解释器直接启动 worker，并显式加载项目依赖；实际启动 PID 必须等于 worker 自报 PID，否则不接纳其观测。
- PID 只标识操作系统中的该次进程，未来可能复用，不作为永久设备身份；进程启动时间、网关新会话和设备 ID 一起用于区分实例。
- 每个 worker 仅管理一个设备会话，标准输出传递受控的状态和事件，最多每 500 ms 回报进程状态。监督程序持续读取管道，设备不在网络事件循环中阻塞等待控制台输入。
- 停止按钮通过该进程的专属管道请求退出，先完成本地停止与最终位置上报，再等操作系统进程退出；5 秒不退出才终止。意外退出保持停止，由用户重新启动。强制外部杀进程只能恢复最近收到的观测位置，不能保证取得杀进程瞬间的位置。
- 启停按设备串行处理，关闭整个演示时禁止再创建新 worker，并清理所属子进程。不会根据前端传入的任意 PID 杀进程。
- 网关快照增加真实地址、当前会话收发计数、连接和心跳时间；不可变快照用原子更新协调计数与状态。无效或过期设备消息不刷新接收计数和遥测。
- 前端每 2 秒刷新获准设备快照；设备状态回报仍走既有 WebSocket，过程观察走本地开发接口。进程观测不可用或网页未认证时分别说明，不把缓存当作当前在线证据。
- 指令追踪由显式诊断订阅开启，只给原控制会话；默认旧客户端不收到额外消息。继续使用原有 64 条可靠队列限制，队列满会断开，诊断不提供持久化或可靠审计承诺。
- 网页/网关侧、设备侧各保留最多 600 条事件，按来源、指令、设备、会话和阶段去重；重复轮询不会无限增长。时钟偏差和回调调度可能使“发送完成”记录晚于对端接收，因此按业务环节排列，不能拿显示时间直接宣称网络耗时。
- 本地启停接口仅在演示模式启用，经同来源检查的 Vite 接口转发；监督端要求服务端私钥，请求不能自行指定后台地址、文件、PID 或任意设备。

## 验证入口与结果

先停止常驻演示，执行回归；再启动演示执行专用验收：

```powershell
.\scripts\stop-demo.ps1
.\scripts\verify-protocol.ps1
.\scripts\verify-simulator.ps1
.\scripts\verify-console.ps1
.\scripts\start-demo.ps1
node .\scripts\verify-proof.mjs
```

本轮实际执行包括协议入口、单独的 Python 验收入口（复用同轮已构建 Java）、前端验收以及专用进程验收。结果：

| 范围 | 结果 |
| --- | --- |
| Java | 85 项通过；新增 2 项诊断开关、所有者隔离与权限测试，真实 TCP 测试补充对端地址和计数断言 |
| 三端互通 | 6 类样例 × 9 组编码/解码 = 54 次通过，新增追踪与诊断快照字段 |
| Python | 28 项通过，并回归真实网关控制与重启恢复；补充设备观测与遥测关联断言 |
| 前端状态 | 10 项通过，新增不伪造缺失来源及有界去重测试 |
| 原有浏览器回归 | 10 项通过，继续覆盖运动、STOP、超时、刷新、认证、恢复和手机布局 |
| 专用三进程场景 | 实际浏览器操作 + 操作系统 PID 检查通过，11 个实际环节齐全；这是一个集成场景，不把节点数量计作测试用例数 |

专用场景核实三个不同实际 PID 与自报一致，三条 TCP 对端不同且会话匹配；正常前进采集完整链路。停止运动中的 RB-002 后，操作系统确认旧 PID 已不存在，另外两台 PID 与会话不变且收发继续。重新启动产生新 PID、新会话，位置不继续变化；旧指令仍 UNKNOWN，缺失的结果节点没有被补成完成。另验证不带来源和跨来源的进程控制被拒绝。桌面、手机截图已查看。

证据：[进程与链路场景](evidence/step-09-process-proof.json)、[协议回归](evidence/step-09-protocol-report.json)、[Python 回归](evidence/step-09-simulator-report.json)、[浏览器回归](evidence/step-09-browser-report.json)。截图位于 `artifacts/proof/processes.png`、`trace.png` 和 `mobile.png`。

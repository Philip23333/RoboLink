## 本次完成

以后机器人要向网页报告“我在哪里”，网页也要向机器人发送“往前走”。机器人端用 Python，服务器用 Java，网页端用 TypeScript，三端首先需要对消息的内容和格式达成一致。

这一步建立了三个模块的基础工程，并约定它们共同使用的消息格式。现在已经能把一条消息转换为二进制数据，再由另外两种语言还原，确认设备编号、位置和指令参数没有变化。

## 技术栈的应用与做法

### 场景一：机器人报告电量和位置

以这条状态为例：“RB-001 电量 87%，位置是 x=1.25 米、y=-2.5 米，朝向 0.5 弧度，目前空闲。”机器人定期上报的这类状态，在项目中称为“遥测”。

这条消息将来要经过以下过程：

```text
Python 模拟机器人生成状态
          ↓
转换成二进制数据，通过 TCP 发给 Java 网关
          ↓
网关识别设备、处理状态，通过 WebSocket 转给网页
          ↓
TypeScript 还原消息，Vue 更新电量和位置
```

其中各技术分别负责：

- **Protobuf 负责“数据怎样表达”。** 在一份 `.proto` 文件里约定电量、坐标、朝向等字段，再生成三种语言都能使用的消息类型和转换工具。把消息变成二进制叫“编码”，还原字段叫“解码”。这样三端不用各自手写一套数据格式，也能明确坐标使用米、朝向使用弧度。
- **Python 负责“模拟机器人产生什么状态”。** 后续模拟器会维护位置和电量，并使用生成的工具编码上报。本次已经用固定状态验证了编码与解码；持续上报和模拟运动尚未实现。Python 依赖放在项目虚拟环境中，避免其他项目的库版本影响模拟器。
- **Java 网关负责“数据从哪台设备来、要交给谁”。** 后续它会管理机器人连接并转发状态。当前 Java 工程已能读取相同的 Protobuf 数据，网络接入和转发留到后续实现。
- **TypeScript 负责“网页怎样读取和使用消息”。** 生成工具 ts-proto 提供字段类型和二进制转换能力。例如把电量字段误当成字符串使用，类型检查就能提前发现部分错误。后续 Vue 使用这些字段更新页面；本次尚未创建页面。

Protobuf 约定格式，TCP / WebSocket 承担传输，Vue 承担界面展示。本次已验证的是消息格式和转换能力，上图中的网络链路和页面还需要继续开发。

### 场景二：用户点击“前进”

假设用户希望 RB-001 以 0.2 米/秒前进 1 秒。对应消息需要写清：目标设备、指令编号、动作、速度和持续时间。

这里已经约定了三类消息：

| 消息 | 在这个场景中表达什么 |
| --- | --- |
| 指令请求 | “请 RB-001 执行这次前进任务” |
| ACK，即设备确认 | “我已经接受这条指令”或“我拒绝这条指令” |
| 执行结果 | “前进已经完成”“执行失败”或“被停止指令中断” |

指令编号用于把请求、确认和结果对应起来。例如用户连续操作两次，后续网关可以据此区分两次执行。当前只定义了这些消息，实际关联、去重和超时处理将在后续实现。

**`oneof` 用来表达“这条消息是哪一种内容”。** 一条消息可以是遥测，也可以是前进请求；在消息对象中设置新的内容分支会替换旧分支。网关和网页后续根据该分支选择处理方式。

**`bigint` 用来防止编号或时间值在网页中变样。** Protobuf 支持 64 位整数，JavaScript 的普通 Number 无法精确表示其中所有整数。TypeScript 因此使用 bigint 保存这些字段，本次也专门用超大整数验证了来回转换后的精度。

### Netty 和 Maven 在哪里发挥作用？

**Netty 将负责网关的网络收发。** 比如机器人连续发送两条状态，TCP 可能让服务器分多次读到第一条，也可能一次读到两条。下一步会用 Netty 按长度头找出每条完整消息，再交给 Protobuf 解析。本次已配置它的传输、编解码和 HTTP 相关依赖，TCP 与 WebSocket 处理还没有实现。

**Maven Wrapper 负责开发时“怎样把 Java 工程构建出来”。** 以后换一台开发电脑，可以用项目自带的入口调用固定版本 Maven，获取依赖、生成 Java 消息类型并编译工程。它服务于开发和构建，不参与某次机器人指令的传输。

## 验证结果

验证使用了两条固定样例：一条是上述电量与位置状态，一条是“前进 1 秒”的指令。

Java、Python、TypeScript 各自生成这两条消息的二进制文件，再由三端分别读取。例如，Python 生成的文件交给 Java 和 TypeScript，读取后检查设备编号、电量、坐标和动作参数是否与预期一致。加上各语言读取自身文件，共有 9 种组合、18 次消息比较，全部通过。

Java 构建和 TypeScript 类型检查也已通过；清理生成目录后再次执行，仍然通过。实际环境为 Java 21、Python 3.12 和 Node 24。

这些结果证明三种语言能正确理解同一份消息。当前通过文件验证，尚未通过真实 TCP / WebSocket 连接发送，也没有驱动机器人运动或更新网页。详细记录见 [验收记录](../acceptance.md)。

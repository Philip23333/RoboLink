# 第二步：TCP 分帧与 Protobuf 编解码

状态：已实现并验收（2026-10-19）。23 项测试与第一步互通回归均通过，尚未创建 Git 提交。范围对应总路线中的第 2 个实现提交。

## 目标与范围

机器人连续上报状态时，服务器需要从 TCP 字节流中找出每条完整消息，再读取设备 ID、电量和坐标。本步提供可安装到每个 Netty 连接的编解码处理流程，不包含注册、心跳或业务路由。

## 本次实现

1. TCP 消息采用 4 字节大端长度头，长度只计算 Protobuf 消息体。
2. 接收时由 Netty 按长度累积与拆分字节，再解析为 Envelope。
3. 发送时先把 Envelope 编码为二进制，再补长度头。
4. 消息体限制为 1–65536 字节，整个帧最多 65540 字节。
5. 非法长度、非法 Protobuf、错误协议版本和缺少 payload 关闭连接；不把原始消息内容写入日志或回传。
6. 发出的 Envelope 也校验版本、内容和大小，防止本端绕过协议约定。
7. 每个连接使用独立分帧缓冲；断线时清理未完成数据。

## 验收标准

- [x] 完整消息、长度头与消息体的任意两段拆分、逐字节输入可正确还原。
- [x] 多条消息合并到一次输入，顺序与字段保持一致。
- [x] 完整消息后附带半条消息时，先交付完整消息并等待剩余数据。
- [x] 固定随机种子的混合拆分测试通过，多个连接不会串用缓冲。
- [x] 正确生成 4 字节大端长度头，65536 字节消息体可收发。
- [x] 零长度、超限及极大无符号长度、非法 Protobuf 被拒绝。
- [x] 错误版本、空 payload、非法出站消息被拒绝。
- [x] 同批数据中坏消息后的正常消息不会继续交付业务处理。
- [x] 连接在长度头或消息体中途断开，不产生消息并释放残帧。
- [x] 真实本机 TCP 测试可收发三条消息，超长头触发连接关闭。
- [x] 第一步三端序列化互通回归通过。

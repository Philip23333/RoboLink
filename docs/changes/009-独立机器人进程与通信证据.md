# 修改说明：独立机器人进程与通信证据

日期：2026-10-20。实现提交：`bc8014b`。

## 本次完成

一键演示现在真正启动三个独立机器人进程。网页新增进程与连接证据、同一指令的三来源追踪，并可单独停止和启动某台设备。原来的三个设备图标之外，现在还能观察后台实例、真实 TCP 会话和逐段回包。

## 场景一：如何知道不是网页里写了三个假机器人

三台设备分别由独立 Python 进程运行，每个进程只维护自己的位置和 TCP 连接。监督程序记录实际启动 PID，并核对设备自己报告的 PID；Java 网关独立记录它看到的 TCP 对端、会话编号、收发计数和心跳。页面把这两份观测并排展示，两端会话匹配后才显示「已匹配」。

Python 的子进程管理负责真正创建和退出设备，asyncio 继续负责每台设备内部的收发与运动；两者承担不同职责。Windows 的虚拟环境可能多出一个启动器，因此本次直接启动匹配的解释器，避免把启动器 PID 当成机器人 PID。监督程序、Java 和网页服务不计入三台机器人数量。

## 场景二：前进指令经过了哪些地方

点击 RB-001 前进，页面生成唯一指令编号。网页记录提交发送，Netty 在处理 WebSocket 请求、完成 TCP 本地写入、收到 ACK 和结果时分别记录事件；机器人在收到指令、写出 ACK、结果及关联遥测时记录自己的事件。Protobuf 把设备与会话、指令编号和真实消息序号带回网页，将这些记录关联起来。

页面共有 11 个观察环节，但只给实际收到的事件打勾。例如设备退出前只发出了 ACK，没有发出执行结果，后面的结果环节就保持「尚无观测」，不能根据“应该执行完了”补齐。完成本地写操作也不等于对端已经收到，因此两种记录分开显示。

Vue 负责合并显示来自三处的观测；有限事件记录和轮询去重避免积压。各进程时钟与异步回调可能不同步，显示时间用于排查，不作为严格的网络延迟成绩。

## 场景三：停止一台，另外两台是否仍在通信

点击「停止 RB-002 进程」，监督程序通过它自己的管道请求退出。该设备先停止动作并报告最终模拟位置，随后操作系统进程退出；网关发现连接断开，网页显示离线。运动中的旧指令保持结果未知，因为没有收齐执行结果。

RB-001 与 RB-003 的进程、会话和上报继续保持。再点击启动 RB-002，会创建新实例并重新认证；本次验收观察到新 PID 和新会话，位置恢复到停止位置，旧运动不重放。PID 不是永久设备身份，未来可能复用，设备仍以 ID 与网关会话区分。

## 验证结果

85 项 Java、28 项 Python、10 项前端状态和 10 项原有浏览器测试通过，6 类协议样例的 54 次三端比较通过。

专用真实浏览器场景另行通过：操作系统核实三个 PID 存活、三个 TCP 对端不同且会话匹配；正常指令的 11 个环节齐全。停止 RB-002 后旧 PID 不存在，其他两台继续上报；重启后旧运动没有恢复，中断链路没有虚构结果。关闭整个演示后，也确认三个所属机器人 PID 均退出。

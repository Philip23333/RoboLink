## 本次完成

上一阶段能从 TCP 中读出消息，这一步开始判断“是谁发来的、这个连接现在还有效吗”。现在可以启动本机 Java 网关，让设备使用自己的编号和凭证注册，上报状态并发送心跳；设备断线或长时间没有合法消息时，网关会清理在线记录。

## 技术栈的应用与做法

### 场景一：RB-001 第一次接入网关

建立 TCP 连接后，设备不能马上随意发送状态，需要先提交“我是 RB-001”和对应凭证。网关核对本地配置，成功后给这次连接分配一个新的会话编号，并告诉设备每隔多久发送心跳。

```text
设备连接 → 提交编号与凭证 → 网关认证
                                 ↓ 成功
                 分配会话编号，加入在线表
                                 ↓
                  接收该设备的心跳与状态
```

**Java 业务处理负责身份规则。** Protobuf 能把消息还原成字段，但不会判断凭证是否正确。本次增加认证步骤，每台设备分别配置凭证，RB-002 的凭证不能用于冒充 RB-001。凭证文件只在服务启动时读取，不会每收到一条心跳就访问磁盘。

**Protobuf 负责表达认证请求和结果。** 成功回应里有会话编号和心跳参数；失败则返回拒绝结果并关闭连接。包含凭证的注册消息不会继续转发给后面的状态处理模块，也不会写入日志。

连接建立后默认最多等待 5 秒注册。即使对方隔一会儿发送几个字节，只要没有完成有效注册，期限到了也会关闭。

### 场景二：机器人重连，旧连接还没退出

假设 RB-001 的旧连接失去了响应，它重新建立连接并认证成功。网关要把在线表切换到新连接，再关闭旧连接。

这里有一个容易出错的时序：新连接已经加入，旧连接稍后才触发“断开”清理。如果清理只看设备编号，就可能把新连接也删掉。

**Java 的并发在线表负责协调不同连接。** 本次清理同时核对“设备编号”和“是不是这一个会话”，旧连接只能删除自己的记录。更新遥测也会核对当前会话，所以旧连接迟到的数据不能覆盖新连接。

**会话编号负责区分同一台设备的不同连接。** 重连后使用新编号，序号可以重新开始。例如旧连接已发到第 100 条，新连接仍可以从第 1 条开始，不会被误判为旧数据。同一会话内的重复或过期序号会丢弃，不刷新在线时间。

### 场景三：页面还没接入，网关怎样知道设备是否在线？

设备默认每 3 秒发送一条心跳，网关回传确认。正常遥测也可以说明连接仍然有效。如果连续 10 秒没有收到合法消息，网关关闭连接并从在线表移除设备。

**Netty 的 IdleStateHandler 负责发现长时间没有有效输入。** 它放在身份、会话、序号和内容检查之后；只有通过检查的消息才刷新这个计时。半条消息、重复序号和不匹配的身份不能让设备一直显示在线。

这只说明设备连接最近仍有有效通信，不表示某条运动指令已经执行完成。指令的 ACK、结果和超时还会在下一步单独处理。

### 场景四：开发者真正启动服务

**Java 21 + Netty 负责运行 TCP 接入服务。** 新增正式启动入口，默认只监听本机 `127.0.0.1:9000`。关闭服务时，会同时关闭已经注册和仍在等待注册的连接，取消定时任务并释放网络线程。

**Python 目前作为联调客户端。** 本次临时启动真实 Java 主程序，用 Python 读取同一份 Protobuf 协议完成注册、上报一条位置、发送心跳，并确认冒用身份和错误凭证会被拒绝。它还不是完整的多机器人模拟器，暂时不执行移动动作。
